# Новый проект с нуля: пошаговый пример

Здесь весь путь от пустой папки до первого merge. Пример проекта — `shop-api`, REST API корзины интернет-магазина. Что такое плагины и какие ещё есть способы установки, описано в [GETTING-STARTED.ru.md](GETTING-STARTED.ru.md).

## Шаг 0. Поставить плагин (один раз на машине)

```bash
claude plugin marketplace add rkaliev/eng-kit
claude plugin install eng-kit@eng-kit
```

После этого плагин работает во **всех** проектах, ставить его заново не нужно.

## Шаг 1. Создать проект

```bash
mkdir shop-api && cd shop-api
git init
claude
```

Claude Code спросит, доверяешь ли ты папке, — ответь «да». Дальше ничего делать не нужно:
- при старте плагин сам загружает правила: сначала проверить скиллы, доказательства прежде «готово», вопросы на развилках, секреты не читать;
- включаются guard и verify-гейт.

## Шаг 2. Описать идею обычными словами

```
Хочу REST API корзины интернет-магазина: товары, скидки в процентах, итог. Деньги считаются точно.
```

Команду набирать не обязательно. Claude видит, что задача подходит под скилл `brainstorming`, и подгружает его. Можно вызвать его и явно: `/eng-kit:brainstorming …`. Что будет происходить:

1. **Классификация вслух:** «Это новый проект, путь Architectural».
2. **Вопросы по одному в сообщении,** например «Где будет работать?», «Нужна ли БД или пока хватит памяти?».
3. **Доменные вопросы подключаются сами.** Задача про деньги, поэтому подгрузится `payments-and-money` с вопросами про валюту, округление и идемпотентность. Их задают сразу, потому что потом менять их дорого.
4. **Выбор стека — всегда твоё решение.** Будет 2–3 варианта (например, TypeScript + Fastify, Kotlin + Spring, Go) с плюсами и минусами и с рекомендацией. Выбираешь ты.
5. **Spec** записывается в `docs/specs/2026-09-26-cart-api.md`, и агент просит его подтвердить.

**Пока ты не сказал «да», код не пишется.** Это жёсткое правило скилла.

## Шаг 3. Каркас и проверки

После твоего «да» агент создаёт каркас официальным инструментом стека: фиксирует версии и добавляет команды тестов, линтера и typecheck. Затем:

```
/eng-kit:kit-init
```

Агент покажет план и после твоего «да» создаст три вещи:
- `.claude/verify.json` — команды проверки проекта, например `npm test` и `npm run typecheck`;
- `.claude/guard.json` — правила guard для проекта;
- deny-правила на `.env` и ключи в `.claude/settings.json`.

Если CLAUDE.md ещё нет, агент предложит собрать его по коду.

## Шаг 4. План

```
/eng-kit:writing-plans docs/specs/2026-09-26-cart-api.md
```

Результат — `docs/plans/2026-09-26-cart-api.md`: маленькие задачи, в каждой точные файлы и тесты, которые доказывают готовность. Потом агент спросит, как исполнять, и порекомендует один из вариантов:
- **inline** — в этой же сессии, дешевле;
- **субагент на задачу** — на каждую задачу свежий агент `implementer` плюс проверка агентом `reviewer`; дороже, но надёжнее.

## Шаг 5. Реализация

```
/eng-kit:implement docs/plans/2026-09-26-cart-api.md
```

- **Отдельная ветка:** на `main` агент без твоего согласия не работает.
- **Ledger:** журнал прогресса `docs/plans/…progress.md`. Если кончится контекст или ты закроешь сессию, следующая сессия продолжит с того же места.
- **Тест первым в каждой задаче:** сначала тест, который падает, потом код, потом зелёный прогон.
- **Если агент захочет закончить раньше времени,** хук вернёт его: «Verify gate: files changed…». Агент прогонит проверки и только потом отчитается.

В итоговом отчёте — изменённые файлы, команды с реальными результатами, каждый критерий и как он проверен, а также что не проверено.

## Шаг 6. Ревью и финиш

```
/eng-kit:requesting-code-review
```

Агент `reviewer` (opus, только чтение) смотрит на diff свежим взглядом. Ты получишь «Подтверждённые» проблемы с `file:line` и доказательствами, «Предположения» и вердикт. Critical и Important агент исправит.

```
/eng-kit:finish
```

Проверки прогоняются ещё раз, затем выбор: merge локально, push и PR, оставить ветку или удалить. **Без твоего выбора ничего не пушится.** На `git push` guard покажет окно подтверждения.

## Работа каждый день

| Ситуация | Что писать |
|---|---|
| Баг | Опиши словами: «итог неправильный при скидке 15%». Подгрузится `systematic-debugging`: корень → падающий тест → один фикс |
| Мелкая задача | `/eng-kit:implement добавить валидацию: quantity > 0` |
| Хочешь сначала оформить задачу | `/eng-kit:new-task …` → `tasks/01-….md` с нумерованными критериями, затем `/eng-kit:implement tasks/01-….md` |
| Просто прогнать проверки | `/eng-kit:verify` |
| Большая новая фича | Снова `brainstorming` → `writing-plans` → `implement` |
| Чужой или старый репозиторий | `/eng-kit:onboarding-existing-codebase` — карта репо, доказанные команды, CLAUDE.md |

## Что остановит guard

- `git push --force` и `git commit --no-verify` — отказ сразу.
- `git push`, деплой, миграции — сначала спросит тебя.
- Чтение `.env` — отказ, секреты не попадут к модели.
- Всё остальное решают обычные разрешения Claude Code.

## Что коммитить в проект

`CLAUDE.md`, `.claude/verify.json`, `.claude/guard.json`, `.claude/settings.json`, `docs/specs/`, `docs/plans/`. Не коммить `.claude/settings.local.json`.

Для команды сделай ещё одно: закрепи плагин в проекте, и коллеги получат его автоматически, когда откроют проект.

```bash
claude plugin marketplace add rkaliev/eng-kit --scope project
claude plugin install eng-kit@eng-kit --scope project
```

## Шпаргалка

| Команда | Зачем |
|---|---|
| `/eng-kit:brainstorming <идея>` | Дизайн до кода |
| `/eng-kit:kit-init` | Настроить проверки, guard и deny-правила проекта |
| `/eng-kit:writing-plans <spec>` | План из маленьких TDD-задач |
| `/eng-kit:implement <задача, план или фраза>` | Реализация с тестами и отчётом |
| `/eng-kit:systematic-debugging <симптом>` | Поиск корня бага |
| `/eng-kit:requesting-code-review` | Ревью агентом `reviewer` |
| `/eng-kit:verify` | Прогнать проверки |
| `/eng-kit:new-task <что сделать>` | Задача с критериями |
| `/eng-kit:finish` | merge / PR / keep / discard |
