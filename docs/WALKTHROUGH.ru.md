# Новый проект с нуля: пошаговый пример

English version: [WALKTHROUGH.md](WALKTHROUGH.md)

Здесь весь путь от пустой папки до первого merge. Пример проекта — `shop-api`, REST API корзины интернет-магазина. Что такое плагины и какие ещё есть способы установки, описано в [GETTING-STARTED.ru.md](GETTING-STARTED.ru.md).

## Шаг 0. Поставить плагин (один раз на машине)

```bash
claude plugin marketplace add rkaliev/eng-kit
claude plugin install eng-kit@eng-kit
```

После этого плагин работает во **всех** проектах, ставить его заново не нужно.

## Шаг 1. Создать проект

```bash
mkdir shop-api && cd shop-api
git init
claude
```

Claude Code спросит, доверяешь ли ты папке, — ответь «да». Дальше ничего делать не нужно:
- при старте плагин сам загружает правила: сначала проверить скиллы, доказательства прежде «готово», вопросы на развилках, секреты не читать;
- включаются guard и verify-гейт.

## Шаг 2. Описать идею обычными словами

```
Хочу REST API корзины интернет-магазина: товары, скидки в процентах, итог. Деньги считаются точно.
```

Команду набирать не обязательно. Claude видит, что задача подходит под скилл `brainstorming`, и подгружает его. Можно вызвать его и явно: `/eng-kit:brainstorming …`. Что будет происходить:

1. **Классификация вслух:** «Это новый проект, путь Architectural».
2. **Вопросы по одному в сообщении,** например «Где будет работать?», «Нужна ли БД или пока хватит памяти?».
3. **Доменные вопросы подключаются сами.** Задача про деньги, поэтому подгрузится `payments-and-money` с вопросами про валюту, округление и идемпотентность. Их задают сразу, потому что потом менять их дорого.
4. **Выбор стека — всегда твоё решение.** Будет 2–3 варианта (например, TypeScript + Fastify, Kotlin + Spring, Go) с плюсами и минусами и с рекомендацией. Выбираешь ты.
5. **Файл задачи** записывается в рабочей ветке в `docs/tasks/2026-09-26-cart-api.md`: твой запрос дословно, затем описание (намерение, критерии, границы, решения, дизайн). Агент просит его подтвердить и после твоего «да» ставит `Status: design approved` и делает коммит. Один файл задачи на одну работу заменяет задачу в трекере: план и журнал выполнения потом дописываются в этот же файл. Он живёт только в рабочей ветке и никогда не попадает в `main`.

**Пока ты не сказал «да», код не пишется.** Это жёсткое правило скилла.

## Шаг 3. Каркас и проверки

После твоего «да» агент создаёт каркас официальным инструментом стека: фиксирует версии и добавляет команды тестов, линтера и typecheck. Затем:

```
/eng-kit:kit-init
```

Агент покажет план и после твоего «да» создаст три вещи:
- `.claude/verify.json` — команды проверки проекта, например `npm test` и `npm run typecheck`;
- `.claude/guard.json` — правила guard для проекта;
- deny-правила на `.env` и ключи в `.claude/settings.json`.

Если CLAUDE.md ещё нет, агент предложит собрать его по коду.

## Шаг 4. План

```
/eng-kit:writing-plans docs/tasks/2026-09-26-cart-api.md
```

План пишется в раздел `## Plan` того же файла задачи, а в `Base:` записывается коммит, от которого он написан. План — это маленькие задачи с чекбоксами `- [ ]`, в каждой точные файлы и тесты, которые доказывают готовность. В конце — блок «Post-implementation»: какую документацию изменение сделает устаревшей (README, docs, CHANGELOG, CLAUDE.md) и что в ней обновить. Потом агент спросит, как исполнять, и порекомендует один из вариантов:
- **inline** — в этой же сессии, дешевле;
- **субагент на задачу** — на каждую задачу свежий агент `implementer` плюс проверка агентом `reviewer`; дороже, но надёжнее.

Это второе одобрение: после твоего «да» статус становится `plan approved`, и файл снова коммитится.

## Шаг 5. Реализация

```
/eng-kit:implement docs/tasks/2026-09-26-cart-api.md
```

План в файле заполнен, поэтому `implement` передаёт его в `executing-plans`.

- **Отдельная ветка:** на `main` агент без твоего согласия не работает.
- **Progress:** раздел `## Progress` файла задачи хранит baseline, дрейф, решения по ходу и строку `Task N: complete (…)` на каждую задачу, а чекбоксы плана отмечаются. Если кончится контекст или ты закроешь сессию, следующая сессия продолжит с того же места.
- **Тест первым в каждой задаче:** сначала тест, который падает, потом код, потом зелёный прогон.
- **Если агент захочет закончить раньше времени,** хук вернёт его: «Verify gate: files changed…». Агент прогонит проверки и только потом отчитается.

В итоговом отчёте — изменённые файлы, команды с реальными результатами, каждый критерий и как он проверен, а также что не проверено.

## Шаг 6. Ревью и финиш

```
/eng-kit:requesting-code-review
```

Агент `reviewer` (opus, только чтение) смотрит на diff свежим взглядом и сверяет его с правилами проекта (CLAUDE.md, `.claude/rules/`, записи решений). Ты получишь «Подтверждённые» проблемы с `file:line` и доказательствами, «Предположения» и вердикт. Critical и Important агент исправит.

Затем агент закрывает файл задачи:
- поведение переходит в тематическую главу, например `docs/02-cart.md`;
- решения и устойчивые правила — в `docs/decisions/` (например, «деньги в целых минорных единицах»);
- тебе показывают его Follow-ups, если они есть, и предлагают начать следующую задачу;
- файл удаляется одним коммитом `docs: remove the task file for cart-api`. Git его хранит.

Если агент забудет, Stop-хук напомнит («Working-docs gate: …»), а guard не откроет PR и не сделает merge в `main`, пока файл есть.

```
/eng-kit:finish
```

Проверки прогоняются ещё раз, затем выбор: merge локально, push и PR, оставить ветку или удалить. **Без твоего выбора ничего не пушится.** На `git push` guard покажет окно подтверждения. Описание PR ссылается на файл задачи по последнему коммиту, где он был (`blob/<sha>/docs/tasks/…`).

## Работа каждый день

| Ситуация | Что писать |
|---|---|
| Баг | Опиши словами: «итог неправильный при скидке 15%». Подгрузится `systematic-debugging`: корень → падающий тест → один фикс |
| Мелкая задача | `/eng-kit:implement добавить валидацию: quantity > 0`. Ограниченная работа остаётся в чате, без файла задачи |
| Хочешь сначала оформить задачу | `/eng-kit:new-task …` → `docs/tasks/2026-09-27-….md` только с описанием и нумерованными критериями, затем `/eng-kit:implement docs/tasks/2026-09-27-….md` |
| Просто прогнать проверки | `/eng-kit:verify` |
| Большая новая фича | Снова `brainstorming` → `writing-plans` → `implement` |
| Чужой или старый репозиторий | `/eng-kit:onboarding-existing-codebase` — карта репо, доказанные команды, CLAUDE.md |
| Новый проект на основе старого | см. раздел «Новый проект на основе легаси» ниже |
| Большой проект из нескольких частей | см. раздел «Большой проект: переписать легаси по частям» ниже |

## Новый проект на основе легаси

Пример: старый проект `legacy-shop` становится новым улучшенным `shop-v2`.

**1. Новый проект, а старый — для чтения**
```bash
mkdir shop-v2 && cd shop-v2 && git init
claude --add-dir ../legacy-shop
```
Работа идёт в `shop-v2`, а `legacy-shop` подключён второй папкой, чтобы Claude мог его читать. Запись вне проекта Claude Code без спроса не делает.

**2. Изучить легаси, ничего в нём не меняя**
```
/eng-kit:onboarding-existing-codebase ../legacy-shop — только чтение.
В legacy-shop ничего не пиши, результат положи в docs/legacy-map.md этого проекта.
```
На выходе — карта старого кода:
- стек;
- реальные команды, проверенные прогоном;
- модули и бизнес-правила в них;
- интеграции;
- рискованные места: деньги, миграции, участки без тестов.

**3. Решить, что сохранить, что улучшить, что выбросить**
```
/eng-kit:brainstorming новая версия legacy-shop по docs/legacy-map.md.
Сохранить поведение корзины и скидок, улучшить архитектуру и тесты, убрать старую админку.
```
Агент задаёт вопросы по одному, стек выбираешь ты из предложенных вариантов. Затем он пишет файл задачи, в описании которого три списка:
- **сохранить** — поведение легаси как контракт;
- **улучшить** — что должно измениться;
- **убрать** — что выбрасывается.

**4. Настроить проверки нового проекта:** `/eng-kit:kit-init`.

**5. План вертикальными срезами**
```
/eng-kit:writing-plans docs/tasks/…-shop-v2.md
```
Каждая задача — одна функция, перенесённая целиком: «каталог», потом «корзина», потом «скидки». На каждую функцию пишутся **golden-тесты**: входы и ожидаемые результаты берутся из легаси и служат приёмочными тестами нового кода; сначала они падают, как любой тест (test-standard, «Porting»). Так доказано, что новое не хуже старого, а намеренные отличия зафиксированы в Decisions файла задачи.

**6. Перенос и проверка**
```
/eng-kit:implement docs/tasks/…-shop-v2.md
/eng-kit:requesting-code-review
/eng-kit:finish
```

**Когда наоборот:** если старая система должна работать в проде, пока её заменяют, отдельный репозиторий не нужен. Работай прямо в `legacy-shop` и заменяй его по частям (паттерн strangler fig, тот же скилл `changing-legacy-code`): новые модули встают рядом со старыми и по одному забирают их функции.

## Большой проект: переписать легаси по частям

Одного файла задачи на такую работу не хватит. Она превращается в несколько независимых задач, у каждой свой короткий цикл, а связывает их раздел **Follow-ups**; отдельного файла со списком частей нет. Пример: переписать `legacy-shop` в `shop-v2`.

**Что вызывается само, а что вручную.** В терминале только `claude`, всё остальное — внутри сессии.
- **Внутри одной задачи скиллы передают работу сами** и останавливаются на каждом гейте, ожидая твоего «да»: brainstorming → (одобрил описание) → writing-plans → (одобрил план, выбрал inline или субагентов) → executing-plans → тесты и verify-гейт → reviewer → finish (твой выбор).
- **Переход к следующей задаче — твоё решение.** Так задумано: после каждой задачи ты смотришь результат.

**Фаза 0. Карта старого** (одна сессия)
```bash
cd shop-v2 && claude --add-dir ../legacy-shop
```
```
/eng-kit:onboarding-existing-codebase ../legacy-shop — только чтение, результат в docs/legacy-map.md
```

**Фаза 1. Первая задача и Follow-ups** (одна сессия)
```
/eng-kit:brainstorming переписать legacy-shop по docs/legacy-map.md. Проект большой, сначала разбей на части
```
Brainstorming называет независимые подсистемы до того, как уточнять любую из них, и предлагает разбиение: задача, которую начинаем сейчас, а остальные — по строке в её `## Follow-ups`, с порядком и контрактами между ними (API, данные, события). Например, первый файл задачи `docs/tasks/…-foundation.md` получает:

```markdown
## Follow-ups

- Каталог: перенести список товаров и поиск из legacy-shop; схему берёт из Фундамента.
- Корзина и скидки: после Каталога; контракт API корзины из docs/legacy-map.md.
- Оформление и оплата: после Корзины; правила payments-and-money, идемпотентные вызовы оплаты.
- Админка: после Каталога, от Корзины не зависит.
- Миграция данных и переключение со старой системы: последней, после всех остальных.
```

**Фазы 2…N. Одна задача = один файл задачи = одна ветка = один PR, в свежей сессии**

Когда задача закончена, агент показывает её Follow-ups и предлагает начать следующую. Выбираешь ты:
```
/clear
/eng-kit:brainstorming Каталог из Follow-ups Фундамента. Поведение переносим из legacy-shop
```
Дальше всё идёт само: файл задачи с описанием → план → реализация с golden-тестами на данных легаси → ревью → долгоживущее из файла переносится в `docs/`, а сам файл удаляется → `finish`. Ещё открытые Follow-ups переходят в новый файл задачи, так цепочка продолжается. Каждый удалённый файл задачи хранит git, а PR на него ссылается.

**Финальная задача: миграция и переключение.** В ней подключатся `payments-and-money` и `security-review`, а guard спросит перед миграциями и деплоем.

**Если сессия прервалась:** `claude --continue`, или новая сессия и фраза «продолжи docs/tasks/…». Раздел `## Progress` покажет, какие задачи плана уже готовы.

**Правила:**
- одна задача = один файл задачи + одна ветка + один PR;
- делить только по настоящим швам: каждая задача даёт ценность или шаг раскатки и зелёная сама по себе; никогда по размеру;
- `/clear` между задачами;
- «субагент на задачу» — для планов с большим количеством независимых задач;
- следующую задачу не начинать, пока текущая не прошла `finish`.

## Формат файла задачи

Каждый файл задачи пишется по шаблону `templates/task.md`. Он заменяет задачу в трекере: разделы до Plan — её описание. У каждого раздела точный заголовок, он отвечает на один вопрос и не повторяет другие. Если писать нечего, в разделе стоит «None» — сам раздел не удаляется.

| Раздел | На какой вопрос отвечает |
|---|---|
| Status / Base / Links | в каком состоянии работа, от какого коммита написан план, связанные задачи и решения |
| Original request | твои слова дословно, в свёрнутом блоке |
| Intent | одна фраза: кто что получит и зачем |
| Context | до трёх предложений: что есть сейчас и что не так |
| Success criteria | таблица «№ — наблюдаемый критерий — как проверяется» |
| Scope | In scope / Out of scope |
| Decisions | решения с тобой; неподтверждённое помечено **assumed** |
| Design | только то, что применимо: компоненты, контракты, данные, ошибки, безопасность |
| Rollout | миграция, флаги, переключение, откат, или None |
| Risks and open questions | риски и вопросы; открытый вопрос блокирует одобрение |
| Follow-ups | независимые куски на потом, по строке; показываются тебе, когда задача закончена |
| Plan | маленькие задачи с чекбоксами `- [ ]`, пишет writing-plans |
| Progress | baseline, дрейф, решения по ходу, `Task N: complete (…)`; без чекбоксов; пишет executing-plans |

**До вопросов** агент собирает карту контекста: файлы, паттерны, типы, конвенции тестов, незавершённая работа, стандарты, стек. Затем пишет намерение, до пяти допущений и открытые вопросы. Вопросы после этого он задаёт по одному.

**Размер.** Описание длиннее примерно 300 строк или с больше чем 10 критериями обычно скрывает несколько тем. Если они делятся по шву, остальное уходит в Follow-ups. Связное изменение не режут под размер: оно получает более длинный план и упорядоченные коммиты.

**`Base:`** — коммит, от которого написан план. Перед выполнением агент проверяет, не изменились ли с тех пор файлы плана, и если изменились, записывает дрейф в Progress и перепроверяет затронутые задачи.

## Статусы файла задачи

У каждого файла задачи во второй строке стоит `Status:`. По нему и новая сессия, и коллега сразу видят, в каком состоянии работа.

| Статус | Кто ставит |
|---|---|
| `draft` | brainstorming (или `/eng-kit:new-task`) пишет описание |
| `design approved (дата)` | brainstorming после твоего «да» на описание; коммит в рабочей ветке |
| `plan approved (дата)` | writing-plans после твоего «да» на план; ещё один коммит |
| `in progress` | executing-plans, когда начинается выполнение |

Финального статуса нет: когда работа закончена, долгоживущее переносится в `docs/`, ты видишь Follow-ups, а файл задачи удаляется. Файл задачи, который заменил новый, удаляется тем же коммитом.

- **Одобряешь только ты.** Описанию и плану нужно по своему «да»; агент его лишь фиксирует.
- **План по черновику не пишется.** Если файл в `draft`, writing-plans попросит сначала одобрить описание.
- **Одобренное обязано быть в git.** Это проверяет хук: если файл задачи в статусе `design approved` или `plan approved` не закоммичен, агент не может закончить ход, пока не закоммитит его (напоминание одно на промпт). На `main` он сначала попросит создать рабочую ветку. Черновики и файлы `in progress` хук не трогает.
- **Реализованное обязано быть удалено.** Файл задачи, у которого в Plan отмечены все чекбоксы, получает такое же напоминание: перенести долгоживущее, показать Follow-ups, удалить.
- Статуса «на ревью» нет: `draft` и есть «ждёт твоего ревью». Кто и когда поменял статус, видно в истории git.

## Документация проекта: что и какой командой создаётся

| Что | Где | Кто создаёт |
|---|---|---|
| Файлы задач (описание, план, прогресс) | `docs/tasks/`, только в рабочей ветке | `/eng-kit:brainstorming` или `/eng-kit:new-task`, затем `/eng-kit:writing-plans`, `/eng-kit:implement` |
| Карта легаси | `docs/legacy-map.md` | `/eng-kit:onboarding-existing-codebase` |
| CLAUDE.md | корень | `/eng-kit:onboarding-existing-codebase` |
| **README, главы `docs/NN-topic.md` и индекс `docs/README.md`** | корень, `docs/` | **`/eng-kit:docs`** — карта документации, после твоего «да» пишет всё по коду и записям решений |
| Одна глава | `docs/NN-topic.md` | `/eng-kit:docs poll-engine` |
| CHANGELOG | `CHANGELOG.md` | `/eng-kit:docs changelog` (из git-истории) |
| Записи решений | `docs/decisions/NNNN-slug.md` | `/eng-kit:docs decision <тема>`, а также исполнение плана, когда принято решение |

**Дальше документация поддерживается сама.** В каждом плане файла задачи есть блок Post-implementation: какую главу обновить, а для новой фичи — какую создать. Исполнение плана делает это в той же ветке, в отчёте появляется строка Docs, а ревьюер считает устаревшую документацию Important.

**Записи решений поддерживаются актуальными, а не копятся.** Одна тема на файл, стабильный номер для ссылок («см. решение 0007»). Когда решение меняется, запись переписывается на месте; когда перестаёт действовать — удаляется. Статуса и даты нет: историю хранит git, а агент читает только те правила, что действуют сейчас.

**CLAUDE.md показывает агенту, где docs.** В его разделе Docs — индекс, таблица «Задача → С чего начать» и какой источник главнее: код, тесты и CI говорят, что есть; записи решений — какие правила действуют и почему; тематические docs описывают. Правила для одной области кладутся в `.claude/rules/*.md` с `paths:` и загружаются только для подходящих файлов.

**Пример для проекта, где есть код, но нет README:**

```
/eng-kit:docs
```

Агент предложит, например:
- README;
- `docs/01-architecture.md`;
- `docs/02-poll-engine.md`;
- `docs/03-alfa-mqr-adapter.md`;
- `docs/04-strangler-routing.md`;
- CHANGELOG.

После «да» он напишет эти документы и внесёт их в `docs/README.md`.

## Что остановит guard

- `git push --force` и `git commit --no-verify` — отказ сразу.
- `git push`, деплой, миграции — сначала спросит тебя.
- Чтение `.env` — отказ, секреты не попадут к модели.
- Создание или merge PR/MR, merge или push в `main`, пока в git есть файл задачи, и коммит файла задачи в `main` — отказ, пока его не перенесут и не удалят. Push самой рабочей ветки только спрашивает. В CI job `working-docs` падает, если `docs/tasks/*.md` отслеживается git.
- Всё остальное решают обычные разрешения Claude Code.

## Что коммитить в проект

`CLAUDE.md`, `.claude/verify.json`, `.claude/guard.json`, `.claude/settings.json`, `.claude/rules/`, `docs/` (главы, записи решений). Файлы задач коммитятся только в рабочей ветке и удаляются до её слияния. Не коммить `.claude/settings.local.json`; личные заметки — в память агента, а не в репозиторий.

Для команды сделай ещё одно: закрепи плагин в проекте, и коллеги получат его автоматически, когда откроют проект.

```bash
claude plugin marketplace add rkaliev/eng-kit --scope project
claude plugin install eng-kit@eng-kit --scope project
```

## Шпаргалка

| Команда | Зачем |
|---|---|
| `/eng-kit:brainstorming <идея>` | Дизайн до кода |
| `/eng-kit:kit-init` | Настроить проверки, guard и deny-правила проекта |
| `/eng-kit:writing-plans <файл задачи>` | План из маленьких TDD-задач в файле задачи |
| `/eng-kit:implement <файл задачи или фраза>` | Реализация с тестами и отчётом; файл задачи с планом уходит в executing-plans |
| `/eng-kit:systematic-debugging <симптом>` | Поиск корня бага |
| `/eng-kit:requesting-code-review` | Ревью агентом `reviewer` |
| `/eng-kit:verify` | Прогнать проверки |
| `/eng-kit:new-task <что сделать>` | Файл задачи только с описанием и критериями |
| `/eng-kit:docs [тема \| changelog \| decision …]` | Документация проекта: README, главы docs, CHANGELOG, записи решений |
| `/eng-kit:finish` | merge / PR / keep / discard |
| «следи за CI» после push | CI через `gh pr checks --watch`: до 2 попыток на упавшую проверку, дальше вопрос; сам агент не мержит |
| `/eng-kit:ci-quality-gates` | CI проекта: команды из verify.json, `gate`, секреты, аудит, миграции, e2e без ретраев. `/eng-kit:kit-init` показывает, всё ли из проверок есть в CI |
| «обнови зависимость X» | `updating-dependencies`: по одной, changelog прочитан, мажор — только с твоим «да» |
