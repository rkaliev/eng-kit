# eng-kit: как это устроено

English version: [ARCHITECTURE.md](ARCHITECTURE.md)

eng-kit — это плагин для [Claude Code](https://code.claude.com), который делает из агента дисциплинированного инженера. Плагин подходит для любого проекта и подстраивается под него по трём независимым осям:
- **где работает код:** web, мобильные приложения (Android, iOS), десктоп (Windows, Linux);
- **что он делает:** от развлекательных приложений до кассовых систем и платежей; там, где ошибка стоит дорого (деньги, фискализация, безопасность), есть отдельные скиллы;
- **в каком состоянии код:** новый проект или существующий, в том числе написанный задолго до агентной разработки.

Поверх этих осей работает один и тот же процесс: дизайн → план → TDD → проверка → ревью → git.

Здесь описано, как устроен плагин и почему он устроен именно так. Что такое плагины, как поставить eng-kit и попробовать его — в [GETTING-STARTED.ru.md](GETTING-STARTED.ru.md).

---

## 1. Идея в четырёх предложениях

1. **Процесс масштабируется по размеру задачи.** Мелкая правка проходит короткий путь, архитектурная — полный путь от файла задачи до ревью. Если сомневаешься, выбирай более тяжёлый путь. Минимум задаёт риск: CI и release-пайплайны, права, auth, секреты, деньги, схема БД и конфигурация деплоя никогда не идут коротким путём, даже если правка маленькая.
2. **Модель сама не решает, что работа готова.** Это решают проверки проекта: Stop-хук возвращает агента к работе, если после правок не было зелёного прогона.
3. **Необратимое и внешнее проходит через человека.** PreToolUse-хук (guard) блокирует опасные команды и спрашивает подтверждение на push, деплой, миграции и публикацию.
4. **Файлы задач остаются в рабочей ветке.** Файл задачи (описание, план и прогресс одной работы) никогда не попадает в базовую ветку: то, что должно жить дальше, переносится в `docs/`, а guard блокирует PR и merge, пока он существует.

## 2. Архитектура

```
┌──────────────────────────── проект ─────────────────────────────┐
│ CLAUDE.md (или @AGENTS.md)   .claude/verify.json   .claude/guard.json │
│ .claude/settings.json (deny на секреты, пин плагина для команды)     │
└───────────────────────────────┬─────────────────────────────────┘
                                │ читают
┌──────────────────── eng-kit (этот плагин) ──────────────────────┐
│ hooks/hooks.json → hooks/hook.ts → lib/hooks.ts                 │
│   SessionStart      bootstrap: правила using-skills в контекст  │
│   PreToolUse        guard: deny / ask / без мнения              │
│   PostToolUse(+Failure)  трекер: правка → «не проверено»        │
│   SubagentStop      вердикт ревью из отчёта reviewer            │
│   Stop              гейты verify, approval, working-docs        │
│   UserPromptSubmit  снова взводит гейты                         │
│ skills/   34 скилла: 28 методических + 6 точек входа            │
│ agents/   reviewer (opus, read-only), implementer (sonnet)      │
│ scripts/  verify.ts, init.ts, install-project.ts,               │
│           test-hygiene.ts, scaffold-template.ts, …              │
│ templates/ CLAUDE.md, task.md, verify.json, ts-monorepo/, …     │
└─────────────────────────────────────────────────────────────────┘
```

**Рабочий цикл:**

```
идея ──/brainstorming──▶ классификация: Spike | Bounded | Architectural
  Spike ─────────▶ проба → рекомендация (код одноразовый)
  Bounded ───────▶ дизайн в чате → «да» → /implement (TDD) → verify → отчёт
  Architectural ─▶ файл задачи → «да» → /writing-plans → «да» → /implement (executing-plans)
                    → долгоживущее в docs/, файл задачи удалить → verify → reviewer-агент
                    → /finish (merge / PR / keep / discard)
баг ──/systematic-debugging──▶ корень → падающий тест → один фикс → verify
чужой репо ──/onboarding-existing-codebase──▶ карта → доказанные команды → CLAUDE.md + .claude/verify.json
```

**Кто за что отвечает:**
- **Скиллы** содержат всю методику.
- **Точки входа** (`implement`, `finish`, `new-task`, `verify`, `kit-init`) — тонкие обёртки. Модель их сама не вызывает (`disable-model-invocation: true`).
- **Агенты** дают свежий контекст для ревью и исполнения задачи плана.
- **Хуки** механически обеспечивают то, что нельзя доверить одному тексту.

---

**Файл задачи** `docs/tasks/YYYY-MM-DD-<slug>.md` пишется по шаблону `templates/task.md` и заменяет задачу в трекере: сверху описание, ниже дописываются план и прогресс:
- Status / Base / Links, исходный запрос дословно, затем Intent / Context / Success criteria / Scope / Decisions / Design / Rollout / Risks / Follow-ups, затем Plan и Progress;
- у каждого раздела точный заголовок и один вопрос, пустой раздел помечается «None»;
- статус: draft → design approved (brainstorming, твоё «да») → plan approved (writing-plans заполняет `## Plan`, твоё «да») → in progress. Bounded-работа остаётся в чате, без файла.

До вопросов агент собирает **карту контекста** (`brainstorming/references/context-map.md`): тикеты, старые планы и docs считаются гипотезами, которые надо сверить с кодом. Затем он пишет намерение, допущения и открытые вопросы. У файла задачи есть `Base:` с SHA коммита, при исполнении проверяется, не ушёл ли код, а журнал ведётся в `## Progress`. У PR есть формат описания, и одна тема на PR.

## 3. Хуки: механика, которую нельзя доверить тексту

Все события обрабатывает один файл, `hooks/hook.ts`. Он читает JSON из stdin, а логика лежит в `lib/hooks.ts` в виде чистых функций, поэтому её легко тестировать.

| Событие | Что делает | Почему так |
|---|---|---|
| `SessionStart` (`startup\|resume\|clear\|compact`) | Кладёт в контекст тело скилла `using-skills` и пути к скриптам кита («Kit root», «Kit verify script») | Без этого скиллы инертны: модель видит только их описания. Матчер `compact` возвращает правила после компакции. По путям из контекста скиллы находят скрипты в обоих режимах установки |
| `PreToolUse` | Guard: `permissionDecision: "deny"` или `"ask"`. На остальные вызовы у него нет мнения. Внутри ревьюера кита (`agent_type` `reviewer` или `eng-kit:reviewer`) shell ограничен просмотром (review gate) | `ask` показывает родной диалог разрешений, в `-p` без UI такой вызов отклоняется. «Разрешить» guard не выдаёт никогда, поэтому собственные правила разрешений Claude Code продолжают действовать |
| `PostToolUse` / `PostToolUseFailure` | Трекер: после Edit/Write/MultiEdit/NotebookEdit рабочая копия «не проверена». Точный прогон команды проверки без pipe отмечает её зелёной, ненулевой код выхода — красной. `gh pr create` или `glab mr create`, замеченный в PreToolUse (по `tool_use_id`, там, где команда начинается), регистрирует свою ветку для review gate, когда вызов успешен или падает после шага с PR | Хуки — отдельные процессы, поэтому состояние хранится в файле на `session_id` в `${CLAUDE_PLUGIN_DATA}` (в режиме папки — во временной директории) |
| `SubagentStop` (review gate) | Когда заканчивает ревьюер кита (`agent_type` `reviewer` или `eng-kit:reviewer`; ревьюеры других плагинов не считаются), хук берёт из `last_assistant_message` строки `Reviewed BASE: <sha>`, `Reviewed HEAD: <sha>` и `Ready to merge: …` и пишет запись вердикта с отревьюенным диапазоном и отчётом, по файлу на запуск ревьюера и коммит, в `<tmpdir>/eng-kit/reviews/<sha1(общей git-директории репозитория)>/`. Записи старше 30 дней удаляются; папке доверяют, только если она принадлежит текущему пользователю. Ревьюеры одного промпта сливаются в худший вердикт. Отчёт без этих трёх строк один раз получает `{"decision":"block"}` (никогда при `stop_hook_active`), чтобы ревьюер их дописал | Запись пишет хук из отчёта самого ревьюера, а не основной агент. Файл на запуск и коммит: параллельные ревьюеры не затирают друг друга, а ревью другой ветки не забывает эту. Поля `agent_type` и `last_assistant_message` и возврат ревьюера проверены живым прогоном (claude 2.1.285), `agent_type` в PreToolUse сабагента — другим (claude 2.1.286) |
| `Stop` | Если рабочая копия не проверена: `{"decision":"block","reason":…}`, один раз на промпт, и никогда при `stop_hook_active` | Модель сама не решает, что работа готова. Одно напоминание на промпт не даёт гейту зациклиться |
| `Stop` (approval gate) | Если файл задачи в `docs/tasks` со `Status: design approved` или `plan approved` не закоммичен — `block` с перечнем файлов, один раз на промпт. В базовой ветке гейт говорит сначала создать рабочую ветку | Одобрение, которого нет в git, может потеряться или незаметно измениться. Скилл об этом просит, но текст модель может пропустить, а хук — нет |
| `Stop` (working-docs gate) | Если в разделе Plan файла задачи отмечены все чекбоксы — `block` с перечнем файлов, один раз на промпт: перенести долгоживущее в `docs/` и `docs/decisions/`, показать Follow-ups и удалить файл | Реализованный файл задачи, оставшийся в дереве, становится устаревшим вторым источником правды |
| `UserPromptSubmit` | Снова взводит все три гейта для нового промпта | — |

`scripts/verify.ts` прогоняет команды из `.claude/verify.json` (иначе из `## Commands` в CLAUDE.md или AGENTS.md) и выходит с кодом 0, только если всё зелёное. Трекер считает такой прогон полным доказательством.

Если проверка упала с ошибкой при обработке PreToolUse, хук отвечает `ask` с текстом ошибки, а не пропускает вызов. В остальных событиях он выходит с кодом 1, и для Claude Code это неблокирующая ошибка: сломанное напоминание не должно останавливать работу. Хук, который не смог запуститься (старый Node, сломанная установка) или превысил таймаут, тоже неблокирующий, и вызов проходит.

## 4. Два режима установки — один источник

- **Плагин** (рекомендуется): namespace `eng-kit:`, обновления по версиям через маркетплейс. Для команды достаточно пина в `.claude/settings.json` (`claude plugin install … --scope project`).
- **Папка `.claude/`**: `scripts/install-project.ts` копирует скиллы в `.claude/skills/`, агентов в `.claude/agents/`, код хуков в `.claude/eng-kit/`. Хуки регистрируются в `.claude/settings.json` из того же `hooks/hooks.json`: `${CLAUDE_PLUGIN_ROOT}` заменяется на `$CLAUDE_PROJECT_DIR/.claude/eng-kit`. Манифест `.claude/eng-kit/manifest.json` помнит, какие файлы записал кит, поэтому повторный запуск обновляет их и не трогает файлы проекта.

Код хуков один и тот же в обоих режимах. Корень кита — родительская папка `hooks/`, а bootstrap ищет скиллы и в `<root>/skills`, и в `<root>/../skills`.

## 5. Скиллы

**Ядро процесса:** using-skills, brainstorming, writing-plans, executing-plans, test-driven-development, systematic-debugging, verification-before-completion, requesting-code-review, receiving-code-review, git-workflow, dispatching-parallel-agents, ci-quality-gates, writing-documentation, updating-dependencies, writing-skills.

**Старт: новый или существующий код:** choosing-a-stack, onboarding-existing-codebase, changing-legacy-code.

**Профиль TypeScript full-stack.** `choosing-a-stack/references/ts-fullstack-profile.md` — один из кандидатов для нового TypeScript-продукта или SaaS с одной командой и Postgres, но не дефолт. По каждой роли там выбор, причина, когда не брать и альтернатива, а версий нет. Если ты выбрал профиль, `node <kit>/scripts/scaffold-template.ts <абсолютный путь>` (`<kit>` — папка, куда установлен пакет кита, или его клон) копирует `templates/ts-monorepo/` (pnpm workspaces, Turbo, веб-приложение на Vite, API на Express, Prisma с Kysely, CI). В шаблоне нет версий: скрипт ставит каждый пакет в старшем стабильном релизе не моложе суток, но не выше мажора стабильного тега `latest`, с точной фиксацией; `@types/node` ставится по мажору Node, а пакеты воркспейса — как `workspace:*`. Четыре практики этого стека лежат в скиллах без привязки к стеку: CI монорепы в ci-quality-gates (только затронутое, при сбое — всё, один gate), одно хранилище, пока нет замера, в backend-services (существующая база несёт очередь, кеш и блокировки, пока замер не покажет, что нужен отдельный сервис), проверяемая граница клиент/сервер в web-frontend и дисциплина зависимостей в updating-dependencies (у каждого override и патча есть причина и условие снятия).

**Платформы:** web-frontend, backend-services, mobile-development (Android и iOS в `references/`), desktop-development (Windows и Linux в `references/`), ui-motion (анимации и жесты на всех платформах: сначала «анимировать ли вообще», затем easing, бюджеты, прерываемость, reduced motion; значения и API платформ в `references/`). В `references/` у web-frontend — состояние и optimistic-обновления, дизайн-система и тексты деструктивных действий; mobile и desktop ссылаются на них.

**Домены с высокой ценой ошибки:** payments-and-money, pos-systems, security-review, observability, database-changes.

**Стоимость контекста.** В каждую сессию попадают только описания скиллов. Тело скилла загружается, когда задача ему соответствует, а `references/` — только когда нужны детали. Поэтому два новых скилла добавляют около 60 токенов, а не свои 1,3 тыс. слов.

**Документация** держится на четырёх слоях:
1. правило в `writing-documentation`: docs в том же изменении и о текущем состоянии;
2. блок «Post-implementation» в каждом плане и шаг обновления docs в `/implement` и `executing-plans`, плюс строка Docs в итоговом отчёте;
3. на ревью устаревшие docs — Important, а не Minor;
4. механические проверки (ссылки, markdownlint, линтеры doc-комментариев, генерация API-справки) — `writing-documentation/references/checks.md` предлагает добавить их в verify и CI проекта.

**Два вида документов.**
- **Рабочие** — файл задачи (`docs/tasks/`) и карта легаси. Файл задачи заполняется по ходу работы (`brainstorming` пишет описание, `writing-plans` — Plan, `executing-plans` — Progress) и записывает намерение и прогресс. Он живёт только в рабочей ветке.
- **Системные** — README, главы `docs/NN-topic.md` с индексом `docs/README.md`, записи решений в `docs/decisions/`, CHANGELOG. Описывают, что есть сейчас. Создаёт их `/docs`, а поддерживают в актуальном виде блок Post-implementation и шаг docs при исполнении плана.

В конце исполнения плана долгоживущее уходит из файла задачи: поведение — в главу про эту фичу, решения и устойчивые правила — в `docs/decisions/`. Пользователь видит его Follow-ups, затем файл удаляется одним коммитом (`docs: remove the task file for <feature>`); git его хранит, а описание PR ссылается на него по последнему коммиту, где он был. Заменённый файл задачи тоже удаляется. Roadmap нет: несколько независимых подсистем становятся отдельными задачами — одна сейчас, остальные по строке в `## Follow-ups`, и у каждой следующей свой файл задачи, ветка и PR. Работа делится только по настоящим швам, а не по размеру: каждая задача даёт ценность или шаг раскатки и зелёная сама по себе.

**Записи решений** — живые документы: `docs/decisions/NNNN-slug.md`, одна тема на файл, стабильный номер для ссылок. Когда решение меняется, запись переписывается на месте; когда перестаёт действовать — удаляется. Статуса, даты и истории изменений нет; разделы — Decision, Why, Consequences, Considered and rejected. Каждый документ хранит только текущую версию, поэтому контекст остаётся маленьким и непротиворечивым.

**Контекст для агента.** В CLAUDE.md проекта (по шаблону `templates/CLAUDE.md`) есть раздел Docs: индекс (`docs/README.md`, `llms.txt`, если есть), таблица «Задача → С чего начать» и какой источник главнее: код, тесты и CI говорят, что есть; записи решений — какие правила действуют и почему; тематические docs описывают; противоречие — это баг, о нём надо сообщить. Строки-подсказки в шаблоне — HTML-комментарии, Claude Code вырезает их из контекста. Правила для одной области кладутся в `.claude/rules/*.md` с frontmatter `paths:` и загружаются только для подходящих файлов; вложенный CLAUDE.md пакета загружается, когда работа читает файлы в нём. Личные заметки — в память агента, а не в репозиторий.

**Точки входа (только вручную):** `/implement`, `/finish`, `/new-task`, `/verify`, `/kit-init`, `/docs`. В режиме плагина их имена начинаются с `/eng-kit:`.

Точки входа — это тонкие обёртки. Остальные скиллы тоже вызываются как `/имя`, поэтому отдельные обёртки над ними не нужны. Имена `plan`, `review` и `debug` не используются, потому что их занимают встроенные команды Claude Code.

## 6. Агенты

| Агент | Модель | Инструменты | Зачем |
|---|---|---|---|
| `reviewer` | opus, effort high | Read, Grep, Glob, Bash. Правки запрещены через `disallowedTools` | Финальное ревью — главное решение по качеству, на нём стоит тратиться. Свежий контекст видит то, что скрывает контекст автора. Читает правила проекта (CLAUDE.md или AGENTS.md, подходящие `.claude/rules/`, записи решений, которые diff затрагивает или цитирует). Читает их на merge-base с удалённой базой (`{RULES_BASE}`) в каждом раунде. В повторном раунде читает находки прошлого раунда через `scripts/review-log.ts`. Guard ограничивает его shell read-only подкомандами git, несколькими read-only командами, worktree по абсолютному временному пути, командами проверки и review-log и отказывает во всём, что его парсер может прочитать неточно; файлы ревьюер читает через Read и Grep. Отчёт кончается строками `Reviewed BASE:`, `Reviewed HEAD:` и `Ready to merge:`, их читает review gate |
| `implementer` | sonnet | все | Одна задача плана по TDD. Статус DONE / DONE_WITH_CONCERNS / NEEDS_CONTEXT / BLOCKED. Отчёт проверяется, а не принимается на веру |

Поля `hooks`, `mcpServers` и `permissionMode` для плагинных агентов Claude Code игнорирует, поэтому они не используются. Это проверяет линтер. Модель переопределяется через `CLAUDE_CODE_SUBAGENT_MODEL` или при вызове.

## 7. Guard: что делает

| Блокирует (deny) | Спрашивает (ask; в `-p` — отказ) |
|---|---|
| `--no-verify`, `git commit -n` | `git push`, публикации и релизы |
| `push --force` / `-f` / `+ref` / `--mirror` | деплой, `terraform apply`, `kubectl apply`, `helm upgrade` |
| рекурсивный `rm` вне проекта и temp | миграции БД, `DROP` / `TRUNCATE` |
| чтение `.env*` (кроме `.example` и подобных), ключей, keystore, credentials (Read, Grep) | `git reset --hard`, `git clean -f`, `branch -D`, `sudo`, `curl … \| sh` |
| запись в `.git/` и в `protectedPaths` | доступ shell к секретным файлам, запись секретного файла |
| `gh pr create/merge`, `glab mr create/merge`, `git merge` в базовую ветку и `git push` в базовую ветку, пока в git есть файл задачи | правка CI и release-пайплайнов (`.github/workflows/`, `.gitlab-ci.yml`, `Jenkinsfile` и подобных) |
| то же, а также push в ветку PR, который открыл агент, без вердикта `Yes` ревьюера для приземляемого коммита с диапазоном до удалённой базы, или в цепочке после любого шага, кроме read-only и команд проверки проекта (review gate); в сабагенте-ревьюере — любая shell-команда, кроме просмотра | правка `.claude/guard.json` (Edit/Write или не read-only shell-команда с этим путём) |
| `git commit` в базовой ветке с файлом задачи в индексе; запись в записи вердиктов (Edit/Write или shell-команда с их путём) | `gh pr merge <номер\|URL>`: голова PR локально неизвестна (review gate) |

Push самой рабочей ветки разрешён (вопрос остаётся, как на любой push).

`.claude/guard.json`: `block`, `confirm`, `allow` (regex), `protectedPaths`, `workDocs` (папки файлов задач, по умолчанию `["docs/tasks"]`; `[]` отключает правило) и `reviewGate` (`false` отключает review gate). `allow` снимает только вопрос и никогда не снимает блок. Отдельная проверка trust не нужна: хуки и настройки проекта Claude Code применяет только после того, как пользователь доверился папке.

Дополнительно `kit-init` добавляет в `.claude/settings.json` родные deny-правила `Read(**/.env)`, `Read(**/*.pem)` и т. п. Это защита в глубину: они работают, даже если хуки отключены.

## Ревью и после push

**Ревью** (`requesting-code-review`, агент `reviewer`):
- **фиксированная серьёзность** по таблице в чеклисте. Critical — секреты, инъекции и authZ, потеря денег или данных, тест ослаблен, пропущен или изменён не так, как разрешает «Changing tests» в test-standard, закоммиченный фокусный тест, удалённая, пропущенная или с ретраями проверка CI, ретраи в конфиге раннера, код-заглушка, подавленные ошибки типов или линтера без причины. Important — критерий без теста или с ручной проверкой, которая не нужна или не согласована, строка Review focus плана без теста, тест без assert или с эхом мока, ожидаемое значение, скопированное из вывода кода или пересчитанное его алгоритмом, тестовый хелпер в продовом коде, фиксированный sleep или настоящая сеть вне sandbox-набора, платежи без теста на sandbox провайдера, POS без списка того, что прогнано на реальном железе, устаревшие docs, нарушенное правило проекта (CLAUDE.md, `.claude/rules/`, записи решений), неотмеченное ломающее изменение, функция длиннее ~100 строк или файл длиннее ~1000 строк;
- **только проверенный код:** ревью, прошедшее, пока правки были не проверены (verify-гейт не зелёный), записывается как Inconclusive; сначала проверки, потом ревью;
- **правила против уговоров:** «так везде в проекте» — это долг, а не разрешение; серьёзность не снижается под давлением аргументов; оцениваются изменённые строки и то, что они ломают;
- **правка правил в самом diff:** если diff меняет правила (манифест агента, конфиг линтера, стандарты), он оценивается по правилам базовой ветки;
- **повторный раунд:** проверяется только новое с прошлого ревью, каждая прежняя находка перепроверяется;
- **правила проекта с цитатой:** находка против правила называет его (файл с заголовком, якорем или ID) и приводит короткую цитату;
- **не дублировать CI:** то, что проверяют команды проверки и линтеры (формат, lint, типы), ревьюер не повторяет — только если проверка падает или отсутствует. Многословный текст — максимум одно сгруппированное Minor;
- **повторный раунд по дефекту:** находки сопоставляются по сути дефекта, а не по формулировке; тот же дефект другими словами — не новая находка;
- **несколько ревьюеров** (платежи, auth, миграции) сливаются по первопричине; на одном `file:line` остаётся более высокая серьёзность, общий вердикт — худший;
- **вердикт** `Ready to merge: <ровно одно из Yes, No, With fixes, Inconclusive>` и строки `Reviewed BASE: <sha>` и `Reviewed HEAD: <sha>`; повторённый шаблон (`Yes / No / …`) вердиктом не считается. Inconclusive — ревьюер не смог прочитать требования, диапазон или правила;
- **без мусора:** никакой похвалы и выдуманных ссылок.

**Review gate** (механика, а не инструкция). Guard запрещает `gh pr create/merge`, `glab mr create/merge`, `git merge` в базовую ветку, `git push` в неё и `git push` в ветку PR, который открыл агент (регистрируется после успешного `gh pr create`/`glab mr create` и забывается, когда голова PR `origin/<ветка>` попала в базу, или через 30 дней), если последний вердикт ревьюера для этого коммита не `Yes` или его диапазон не доходит до удалённой базы. Доходит, если `Reviewed BASE` записи лежит в базовой ветке push-remote (иначе `origin`, иначе любого remote; в локальной базе — только когда её не отслеживает ни один remote) или сам является коммитом, ревью которого засчитывается по тому же правилу, не больше 20 раундов и 300 вызовов git. Раунд должен начинаться с самого нового отревьюенного коммита под ним, чтобы не пропускать находки раунда. Повторный раунд смотрит только новые коммиты, а находки прошлого раунда его ревьюер читает через `scripts/review-log.ts`, а не со слов автора. Пустой диапазон, цепочка, разорванная rebase, и запись без диапазона ничего не покрывают. Запись вердикта пишет хук `SubagentStop`; ревью, прошедшее, пока правки сессии были не проверены (в проекте с командами проверки), записывается как `Inconclusive`. Вердикт покрывает ровно тот коммит, который ревьюер отревьюил: любое изменение после него (новый коммит, amend, rebase на свежую базу, правка документации, удаление файла задачи) требует нового ревью, и ветка только с документацией ревьюится так же, поэтому финальное ревью идёт последним — после docs, удаления файла задачи и rebase. Коммиты, уже лежащие в удалённой базе, ничего нового не приземляют. `cd <dir>` и `git -C <dir>` отслеживаются от cwd сессии, поэтому ветка worktree проверяется там, где выполняется команда. Приземление в цепочке после любого шага, кроме read-only и команд проверки проекта (`git commit … && gh pr create`, `git switch main && git merge …`) запрещено: guard не видит, что оно приземляет. `gh pr merge <номер|URL>` спрашивает, потому что голова PR локально неизвестна; `gh pr merge <ветка>` и `gh pr create --head <ветка>` проверяют эту ветку. `With fixes`, `No` и `Inconclusive` не пропускают: исправить и отревьюить новый диапазон. Находку, от которой автор отказался без правки кода, снимает повторное ревью в следующем промпте, после того как пользователь увидел аргументы. Отключает гейт только пользователь: `"reviewGate": false` в `.claude/guard.json`; перед правкой этого файла (Edit/Write или shell) guard спрашивает, а запись в записи вердиктов запрещает. Защищает от забытого или пропущенного ревью, а не от агента, который намеренно подсовывает ревьюеру готовый ответ.

**Ответ на ревью** (`receiving-code-review`): каждое замечание либо исправлено, либо на него дан ответ; ни одно не пропускается молча. Нельзя писать «решено», пока открыт блокер или пока повторное ревью не закрыло находку.

**Люди в цепочке** (`ci-quality-gates`, только с твоего «да»): одно обязательное одобрение человека (AI-ревью его дополняет, но не заменяет) и CODEOWNERS на файлы, которые управляют остальными: манифест агента и его папка, path-правила, CI, `docs/decisions/`, конфиги линтера и типов.

**После push** (`git-workflow`):
- CI отслеживается инструментом хостинга, а не самописным циклом;
- на каждую упавшую проверку — не больше двух попыток с найденной причиной, дальше вопрос тебе;
- агент никогда не мержит сам;
- rebase своей ветки — только `--force-with-lease=<ветка>:<sha>`.

**Процессы:** dev-серверы и watchers работают в фоне; агент останавливает только то, что запустил сам.

## Два контура проверок: сессия и CI

- **Сессия агента.** TDD, verify-гейт после каждой правки, гейты approval и working-docs, guard, ревью. Ловит проблему сразу, пока агент работает.
- **CI проекта** (`ci-quality-gates`). Работает на каждом изменении, кто бы его ни сделал, и не зависит от хуков и модели:
  - минимум всё из `verify.json`;
  - джоба `working-docs`, которая падает на любом `docs/tasks/*.md` в git, чтобы файлы задач не попадали в базовую ветку ни от какого автора;
  - один обязательный `gate` (в нём `e2e`, только если такая джоба есть в проекте);
  - по стеку и только с твоего «да»: гигиена тестов, e2e без ретраев, чьи JUnit-отчёты проверяет `--junit test-results/` (только отчёты), sandbox провайдеров отдельной джобой, поиск секретов и аудит зависимостей, миграции и дрейф схемы, контракты, покрытие как пол по расписанию.
- **Скрипт `test-hygiene`** (`scripts/test-hygiene.ts`): один файл без зависимостей, нужен только Node ≥22.18, какой бы ни был стек проекта. `kit-init` предлагает его и копирует в `.ci/test-hygiene.mts` (ES-модуль, что бы ни говорил `package.json` проекта) только с `--test-hygiene` (`node <kit>/scripts/init.ts --test-hygiene`) после твоего «да». Тот же флаг заменяет более старую копию (версии сравниваются как числа), а пробел в CI виден в том же прогоне. Запускают его джобы `test-hygiene` и `e2e` из шаблонов ci-quality-gates. Он проверяет:
  - фокусные тесты и skip без ссылки на задачу (`#123`, URL или `ABC-123`; причины словами мало, кроме skip по платформе или режиму тестов, чья причина начинается с `platform:` или `mode:`) в JS/TS (Playwright `test.describe.only/skip/fixme`, Cypress, раскладки Mocha и Nest), Python, JVM, Go, Swift, .NET, Gherkin; фиксированные sleep; ретраи в конфигах раннеров и в коде тестов (`this.retries`, `describe.configure`, pytest `flaky`);
  - `--junit <dir>` сам по себе проверяет только отчёты: отсутствующий или пустой, либо заявленное число тестов не совпадает с прогнанными (упавший шард).

  В существующем проекте это храповик: считаются только строки, которые добавляет изменение (переименования отслеживаются), а старый долг показывается в сводке и не блокирует (`--all` проверяет все строки). Без merge base скрипт останавливается с сообщением: CI нужен `fetch-depth: 0`, а в GitLab — явный fetch целевой ветки. `test-hygiene: allow <причина>` помечает строку, где паттерн и есть проверяемое поведение; allow без причины сам считается нарушением, а allow, скрывающий запрещённый skip, ретрай или sleep, — только с твоего согласия. `.ci/test-hygiene.json` добавляет тестовые файлы, исключения и паттерны. Рядом — родные линтеры стека (таблица в `ci-quality-gates/references/ci-templates.md`).
- **Команды проверки в Turbo-монорепе.** Если есть `turbo.json` (или `turbo.jsonc`, комментарии допустимы), `kit-init` определяет одну команду `<exec> turbo run typecheck lint test` из объявленных в нём задач; ключ `pkg#task` объявляет `task`, а `<exec>` — `pnpm`, `yarn`, `bunx --no-install` или `npx --no` по lockfile, так что запускается только локально установленный turbo. Раздел Commands манифеста по-прежнему главнее, а нечитаемый `turbo.json` или без этих задач отдаёт выбор скриптам `package.json`. Один `pnpm-workspace.yaml` выбирает pnpm.
- **Связка контуров:**
  - `kit-init` механически сверяет, что CI запускает каждую команду проверки, содержит джобу working-docs и запускает `.ci/test-hygiene.mts`, если он есть в проекте, и сообщает, если копия старше версии кита;
  - ревью считает Important отсутствие команды в CI и нарушенное правило проекта, а удалённую, пропущенную или с ретраями проверку — Critical.
- **BDD** — опциональный приёмочный слой (`test-driven-development/references/bdd.md`). Каждый видимый пользователю критерий файла задачи — ровно один сценарий с тегом критерия. Получается цепочка «критерий → сценарий → CI», а теги проверяет ревью по файлу задачи.

## Тестирование

Основа — железное правило TDD: сначала падающий тест, затем минимальный код, затем прогон всего набора. Все остальные правила тестов живут в одном месте — в стандарте `test-driven-development/references/test-standard.md`; TDD, BDD, writing-plans и чеклист ревью ссылаются на него, а не пересказывают:
- **ожидаемые значения** берутся из критерия файла задачи, а не из вывода кода. Единственное исключение — характеризационные тесты легаси: `*.char.test.*` (или тег стека), они по замыслу проходят с первого запуска и не считаются покрытием нового поведения. Эталонные данные при портировании — приёмочный тест, который сначала падает, а не характеризационный;
- **сначала красный:** каждый новый тест видят падающим, кроме характеризационного;
- **тест должен окупаться:** нет тестов на константы, конфиг, форму схем, «рендерится», эхо мока; одинаковые случаи объединяются в параметризованный тест; снапшоты маленькие и инлайн;
- **структура и имена:** Arrange–Act–Assert, одно поведение на тест, имя = субъект + обстоятельство + результат; тестовые хелперы живут в тестовом коде;
- **моки:** фейкуются только неуправляемые зависимости; своя БД и очереди в интеграционных тестах настоящие. Sandbox провайдеров — отдельный набор и отдельная джоба CI, единственное место, где тест ходит в сеть;
- **детерминизм и изоляция:** время и случайность под контролем, сети нет, есть прогон не в UTC; ожидание — по условию с одним потолком на проект, никогда не фиксированный sleep; тесты работают в любом порядке и параллельно; отсутствующая тестовая инфраструктура (БД, контейнер, эмулятор) роняет прогон, а не пропускает тест;
- **без ретраев:** тест никогда не перезапускается — ни в конфиге раннера, ни в CI, ни циклом. Ожидание условия (web-first assertions, `expect.poll`, `waitFor`) — не ретрай. Flaky считается исправленным, только когда выполнены пять критериев: найдены падающий прогон и граница, устранена первопричина, повторный прогон зелёный на том же коммите, зелёный в той конфигурации, где падал, весь набор зелёный;
- **критерии и уровни:** с BDD у видимого пользователю критерия ровно один сценарий с его тегом; у любого другого критерия — хотя бы один тест на самом дешёвом уровне, который показывает его так, как видит пользователь или вызывающий код; e2e без BDD — только критичные сценарии, по одному пути на тест;
- **ручная проверка** заменяет тест только там, где автоматизация невозможна (реальное железо, ревью стора, фискальное устройство, физическая подпись): в файле задачи — причина, ты согласен, отчёт говорит, что она выполнена. В остальных случаях критерий без теста — пробел;
- **outside-in с BDD:** сначала пишется сценарий и видно, как он падает, затем unit-циклы TDD ведут код, а прошедший сценарий закрывает критерий. Unit-тесты под ним проверяют собственный контракт своего модуля и остаются; не пишется только unit-тест, который проверяет тот же пользовательский результат, что уже доказывает сценарий;
- **изменение тестов:** удаление теста вместе с его поведением или теста, который ничего не защищал, требует только причины в коммите; правка assert, удаление теста, чьё поведение осталось, skip или карантин — только с твоего согласия и отдельным коммитом; у skip есть ссылка на задачу (кроме skip с причиной `platform:`/`mode:`). `test-hygiene: allow <причина>` — для паттерна, который и есть проверяемое поведение; скрыть им запрещённый skip, ретрай или sleep можно только с твоего согласия, и ревью оценивает это как сам паттерн;
- **покрытие** — пол, а не цель; визуальные эталоны создаются только в CI.

План называет тест для каждого критерия, а описание PR — как каждый новый тест видели красным. Ревьюер проверяет правила с фиксированной серьёзностью из чеклиста. Механический слой (скрипт `test-hygiene` и линтеры стека) ci-quality-gates добавляет только с твоего «да».

## 8. Принципы, заложенные в плагин

1. Три пути процесса вместо одного тяжёлого, чтобы мелкие задачи не тонули в бюрократии.
2. Методика — в скиллах, механика — в хуках, точки входа — тонкие. Правила готовности живут в одном месте.
3. Встроенное не дублируется. Для разведки есть `Explore`. Модели задаются через frontmatter (`model:` у агентов, `effort: high` у тяжёлых скиллов), своего конфига маршрутизации нет. Пин для команды — родной `--scope project`.
4. Никаких узких вендорных скиллов. Проектная специфика — в CLAUDE.md проекта.
5. Подтверждение на любой `git push`. Своим веткам его снимает узкое `allow` в `.claude/guard.json`, например `^git push origin feat/`.
6. Скиллы на английском: так точнее срабатывание. Документация — на английском, у каждого файла есть русская версия (`*.ru.md`).

## 9. Как это проверено

- **`npm test`**:
  - guard (блок, вопрос, allow, конфиг, пути, temp, рабочие документы, review gate: запись вердикта, слияние вердиктов, параллельные запуски, код после ревью, удаление файла задачи, удалённая база, rebase, worktree и `cd`, приземления в цепочке, `gh pr merge` по номеру, запись через shell, ревью непроверенных правок как Inconclusive, цепочка диапазонов (узкий BASE, пустой диапазон, rebase, 20 раундов, без remote), review-log, push в ветку открытого PR, allowlist shell ревьюера, проект через symlink);
  - парсер команд и правило доказательства;
  - обработчики хуков (SessionStart, PreToolUse для Bash, PowerShell, Read, Grep, Edit, NotebookEdit; трекер и Stop-гейты);
  - `hook.ts` через stdin/stdout, включая нечитаемый ввод (код 1); `respond()` с падающим обработчиком (PreToolUse спрашивает, остальные события выходят с кодом 1);
  - `verify.ts`;
  - `test-hygiene.ts` (правила на 7 языках, храповик с переименованиями, нет merge base, только JUnit-отчёты, конфиг, CLI);
  - `kit-init` (в том числе пункт test-hygiene: предложен, копируется с `--test-hygiene`, старая копия видна в отчёте и заменяется по флагу, CI без него виден в том же прогоне);
  - `install-project` (установка, обновление, конфликты, хуки без дублей);
  - линтер скиллов и агентов, согласованность манифестов.
  - шаблон `ts-monorepo` (нет версий, `scaffold.json` называет существующие воркспейсы, действия закреплены по SHA) и скрипт scaffold (отказ для непустой папки, планируемые установки, `.nvmrc` и `packageManager`);
- **`npm run typecheck`** и **`claude plugin validate .`**.
- **`template-smoke`** (`.github/workflows/template-smoke.yml` в собственном CI кита, раз в неделю и на PR, затрагивающих шаблон или скрипт scaffold): разворачивает `ts-monorepo` в чистую папку, запускает `pnpm turbo run typecheck lint test` и `prisma migrate deploy` на Postgres. Он вне `gate` и релиза: красный означает, что экосистема сдвинулась и шаблон надо поправить.
- **Живой прогон `claude -p`** на копии `examples/demo`:
  - bootstrap;
  - deny на `git commit --no-verify`;
  - ask и отказ на `git push`;
  - Stop-гейт после Edit без тестов вернул агента к `npm test`;
  - режим папки: bootstrap и guard из `.claude/eng-kit`;
  - установка через `--scope project` из локального маркетплейса;
  - review gate (claude 2.1.285, `--plugin-dir`, копия `examples/demo` с внесёнными дефектами): PR без ревью — deny; агент `reviewer` нашёл float-округление денег (Critical, с цитатами правил из CLAUDE.md, задачи и чеклиста) и непокрытый критерий, вердикт `No` — снова deny; после исправлений повторный раунд по новому диапазону перепроверил старые находки, `Yes` — guard пропустил `gh pr create`.

**Не проверено:** Windows (инструмент PowerShell и запуск хука через `cmd`), живой прогон агента `implementer`.

**Известные ограничения review gate:** однострочник интерпретатора всё ещё может спрятать путь от проверок shell; гейт защищает от забытого ревью, а не от агента, который намеренно подсовывает ревьюеру вердикт; он видит только PR, открытые этим агентом, но не открытые в браузере или другим инструментом; диапазону, который назвал ревьюер, гейт доверяет; allowlist shell ревьюера — проверка парсером, которая отказывает во всём, что не может прочитать точно, а не песочница; remote-tracking refs локальны, поэтому `git update-ref` может подделать влитый PR или уже приземлённый коммит; хук, который не смог запуститься, превысил таймаут или получил нечитаемый ввод, пропускает вызов; парсер команд основного агента не разбирает heredoc и комментарии `#`, поэтому приземление после них может остаться незамеченным; при установке в проект агент может править файлы самого кита; без определимой базовой ветки (нет `origin/HEAD`, нет `main`/`master`) он ничего не делает.

## 10. Как развивать

- Новый скилл пишется по `writing-skills`: сначала сценарий без скилла (RED), потом минимальный скилл. Затем `npm test`, `claude plugin validate .` и строка в этом документе.
- Правило, которое можно проверить механически, живёт в хуке, в `permissions` settings.json или в CI, а не в тексте скилла.
- В шаблоне нет версий: они ставятся из реестра при scaffold, а `template-smoke` показывает, когда экосистема сдвинулась.
- Доменные плагины под конкретную компанию (конкретный эквайер, ОФД) лучше делать отдельным плагином и подключать через `dependencies` в `plugin.json`.
