# Review gate

The guard denies opening or merging a PR/MR, merging into the base branch, pushing to it, and pushing to the branch of a PR you opened, unless the kit reviewer's last verdict is `Yes` for the commit being landed and covers the whole branch. The hook records the verdict and the report from the reviewer's own `Reviewed BASE:`, `Reviewed HEAD:` and `Ready to merge:` lines when the reviewer finishes; you never write them yourself.

- **A verdict covers exactly the commit the reviewer reviewed** (its `Reviewed HEAD`). Any change after it needs a new review: a new commit, an amend, a rebase onto a newer base, a docs edit, deleting the task file. A branch that changes only documentation is reviewed the same way. So review last: after docs, the task-file removal and any rebase. Commits already on the remote base land nothing new and need no review.
- **The range must reach the remote base.** A review counts when its `Reviewed BASE` is on `origin/<base>` (the local base branch when there is no remote), or is itself a commit whose review counts by the same rule. A repeat round can review only the new commits, and the chain still covers the whole branch, up to 20 rounds. A rewritten history breaks the chain: review from the merge-base again. An empty range (`BASE` = `HEAD`) covers nothing, and so do records written before 0.14.0, which have no range: after updating, review each branch once more.
- **Earlier findings come from the store.** A repeat round's reviewer runs `node <kit root>/scripts/review-log.ts <previous HEAD>`, which prints that round's reports, and re-checks every finding in them. You don't pass the findings on yourself.
- **A PR you opened is a landing target.** After a successful `gh pr create` or `glab mr create`, pushing to that branch needs the same review. The branch is forgotten once the PR's head (`origin/<branch>`) is on the base, or after 30 days. A PR opened outside this agent (in the browser, by another tool) is not seen.
- Land in a command of its own: a landing chained after anything but read-only steps (`cd`, `git status`/`diff`/`log`/`add`/`fetch`, `cat`, `grep`…) and the project's verification commands is refused, because the guard can't see the commit it would land. A `cd` the guard can't follow (a variable, `$(…)`, a nested subshell, a missing folder; a `cd` inside one `( … )` is followed and ends with it) or `-R` to another repository is refused too. `gh pr merge <number>` asks, because the PR's head isn't known locally; name the branch, or merge from it (the remote branch is checked as well).
- **The reviewer only reads.** In the reviewer subagent the guard runs only inspection commands (`git diff`/`log`/`show`/`blame`…, read-only tools), `git worktree add`/`remove` in the temp folder, the project's verification commands and review-log. A substitution, a writing redirection, git's `-c` or `--output`, or anything else is refused.
- If the reviewer's report lacks the three lines, the hook sends it back once to add them; a second miss counts the run as failed: `Inconclusive` for the commit it reviewed, within that prompt. A review of a later commit is unaffected.
- A review counts only for verified code: one that ran while edits were unverified (the verify gate wasn't green) is recorded as `Inconclusive`. Run the checks first, then review.
- `With fixes`, `No` and `Inconclusive` all block: fix, then re-review the new range.
- Parallel reviewers dispatched for one user prompt combine to the worst verdict. A finding you pushed back on without changing code is withdrawn by a re-review in a later prompt, after the user has seen your reasoning.
- If the guard itself crashes while checking a call, it asks you instead of letting the call through.
- Only the user can waive the gate (`"reviewGate": false` in `.claude/guard.json`, whose edits the guard asks about). A self-review in a separate pass does not satisfy the gate.
